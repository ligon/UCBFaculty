* The plan we converged on

Move UCBFaculty's distribution off private GitHub onto a fully public
PyPI release, while keeping the data repository (=RawData=) private on
github.com.  Onboarding for the eight-or-so committee users continues
to require a personal GitHub account + =gh auth login= + collaborator
status on =RawData= --- but the package itself no longer requires any
GitHub auth to install.

Alternatives considered and rejected (see commit / chat history for
reasoning):
- Box / bConnected Drive for =RawData= --- adds streaming-vs-mirror
  configuration failure modes; gives no benefit over =git pull= which
  already works.
- =github.berkeley.edu= (Enterprise GitHub + CalNet) --- SAML SSO
  requires recurring re-authorization on every key/token after each
  CalNet session expires; too much friction for committee users.
- Public =RawData= --- ruled out on revocation grounds: a public
  ciphertext store can never have access revoked from someone who has
  already downloaded it; private repo bounds exposure to "people who
  once had collaborator status."

* Mancosu / Wallace email swap (mostly resolved)                    :bug:

Surfaced on 2026-05-21 in the Faculty Lookup tab: Paolo Mancosu's row
(2025-26 Chair, Philosophy) displayed =rjw@berkeley.edu=, which is
R. Jay Wallace's personal address.

** Diagnosis

The email-canonicalisation dictionary at
=RawData/email_dictionary.json= (previously line 5) mapped
=philo12a@berkeley.edu= as a variant of =rjw@berkeley.edu=.
=philo12a@berkeley.edu= is the Philosophy 12A course / role mailbox,
owned by whoever teaches the course at the time; aliasing it to one
specific person's personal email bakes in a stale identity that
misfires the moment the assignment changes.

The mis-mapping was then applied by the canonicalisation code:
- =merge_features.py:110= : =corrected = email_dictionary.inverse_d[email]=
- =new_feature.py:543=    : =processed_df.rename(index=EMAIL_DICTIONARY.inverse_d)=

When two source rows --- Wallace's =rjw@berkeley.edu= and Mancosu's
=philo12a@berkeley.edu= --- both got rewritten to =rjw@berkeley.edu=,
the index became non-unique.  Downstream lookups keyed by canonical
email returned whichever row pandas resolved first, and the displayed
Email column showed the canonical (=rjw=) regardless of which
person's other fields survived the collision.

** What landed

1. *Data fix.*  =RawData= commits =0582583= (add Mancosu's canonical
   entry) and =5b1c0ed= (remove the =rjw= / =philo12a= entry
   entirely).  =philo12a@berkeley.edu= now passes through
   un-canonicalised; records that reference it appear as-is rather
   than silently inheriting any individual's identity.
2. *Code defense.*  =UCBFaculty= commit =e731300=:
   =_warn_on_email_canonicalisation_collision= logs at WARNING when
   the rename produces duplicate index entries with distinct
   FullName values.  Diagnostic, not corrective: the pipeline still
   completes; the operator can see which identities collided.
   Same-canonical same-FullName collisions stay silent (intended
   outcome for one person with multiple email forms).

** Still open

- *Source verification.*  Nobody has actually opened the encrypted
  source spreadsheet (likely =COMS - Senate faculty report
  01202026.xlsx.gpg=) to confirm that Mancosu's row contained
  =philo12a@berkeley.edu= as theorised.  If the theory holds, the
  =RawData= fixes above resolved the immediate symptom.  If the
  source row contains some *other* mis-aliased email, the same fix
  pattern (remove the variant mapping, let the role mailbox stay as
  itself) applies again --- but the warning from =e731300= will now
  surface any future case loudly instead of silently.
- *Audit other role mailboxes.*  The =rjw / philo12a= pair existed;
  there may be other course-number or role mailboxes among the
  remaining five dictionary entries that deserve the same scrutiny.
  =faberb@berkeley.edu / benfaber@econ.berkeley.edu= and
  =rhstanton@berkeley.edu / richard.stanton@berkeley.edu= look like
  personal-email-variant pairs (safe); =tmhickey / soknebtunis= and
  =kyriakos / kyriakos@me.berkeley.edu= could be either --- a quick
  check would close that loop.
